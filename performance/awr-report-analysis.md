# AWR 报告诊断（vb_tool awrrpt 产物）

## 概述

本文件定义从一份 VastBase AWR 报告到一份诊断报告的完整流程。输入是 vb_tool
`awr awrrpt` 生成的 HTML（建议同时提供其配对的 analyze_log_v2 错误/慢 SQL 报告，
两者默认打包为 `awr_<b><e>.tar`）；产出是 `<输入名>_analyze.html` 诊断报告，
含分钟级与 5 分钟桶趋势图。

方法分工：预提取器（`scripts/extract.py`）负责 HTML 解析、时间轴计算与证据切片——
结构化与算术交给代码，因为手抄表格数字和跨章节对时容易错；诊断推理由模型依据
本域知识文件完成。所有报告中的数值只能来自 digest，这是防幻觉的硬边界。

配套阅读：诊断导图（症状→章节导航、三件套、不过度诊断）查 `diagnostic-map.md`；
章节与列的语义查 `awr-report-reference.md`；指标口径查 `metrics.md`；数字为什么
能当证据（三本账/DB Time 边界/事件账本污染）查 `awr-principles.md`；事件溯源查
`wait-events.md`；瓶颈取证查 `bottleneck-patterns.md`；参数对照查 `parameters.md`；
日志联动查 `log-analysis.md`。

## 输入与工作区

两个固定目录（域内共享，与知识文件分离）：

1. **输入目录** `vastbase/workspace/inbox/`
   - 放 awrrpt HTML + 配对 analyze_log HTML；或服务器上下来的 `awr_<b><e>.tar`
     （先 `tar -xf` 解包得两份 HTML）
   - 用户未特殊指明时，取时间窗**最新的成对** awrrpt+logrpt（按文件名中的
     YYYYMMDDHHMMSS 排序）；用户点名文件或时间窗则用点名的
   - 只有单份 awrrpt 也能分析（日志轴降级，报告写明局限）
2. **源码目录** `vastbase/workspace/src/`
   - 解析顺序：目录里有源码树（存在 gausskernel/backend）→ SOURCE_ROOT 文件
     指定的路径 → 默认 `<openGauss-6.0.0-src>/`

配套命令：`vb_tool se <event>`（417 事件离线知识库，见 `wait-events.md`）。

## 预提取

```bash
python3 scripts/extract.py <awrrpt.html> [analyze_log.html ...]
```

同目录产出三件，职责固定：

| 产物 | 内容 | 职责边界 |
|---|---|---|
| `<输入名>_digest.txt` | 章节 KV、Top 表、派生指标、异常时段标注、多源对齐表 | **所有数值引用的唯一来源** |
| `<输入名>_charts.json` | 分钟级 OS 序列 + 5 分钟桶（活动会话/刷脏/长事务）+ 问题时段带 | 趋势图数据，整个粘进报告模板（时段带仅存于 JSON，渲染器不画图） |
| `<输入名>_params.txt` | 全量 GUC + sysctl | 参数查证 |

健康总览（第 2 步前的机械闸）：`python3 scripts/overview_table.py <输入名>_digest.txt`
→ 45 项固定检查（2026-11-05 复数统一）（阈值集中 RULES，awrrpt+logrpt 两报告全覆盖），亮 ■/▲ 的项按
FORM_OF 自动挂 P1~P12 形态闸。**检查项全量清单与两报告能力总账见
`check-inventory.md`（表 A/B/C/D）**——能诊断什么、边界在哪、哪些靠人工项兜底，
以该文件为准。

## 分析流程

六步顺序执行。每步的结论（含排除）都保留下来，报告只呈现面向读者的交付内容。

### 第 0 步：有效性预检

为什么先做：窗口内实例重启或计数器回卷会让一切差值作废，不预检的话后面所有
"窗口增量"都在拿无效数据下结论。

| 检查 | 看哪 | 不通过时 |
|---|---|---|
| Elapsed ≥ 60s | 报告头 | 窗短，比例类结论降档并在报告声明 |
| 窗内无重启/计数器回卷 | 报告头 Startup Time；Load Profile 的 negative delta WARNING | 差值作废，只能用瞬时值（gauge） |
| 快照对完整 | 报告头 Begin/End/DB Time | 标数据缺口，受影响分支写"数据不足，未判定" |
| OS 分钟序列可用 | OS Statistics 各 per-minute detail | 时间轴降级为 5 分钟桶或仅整体画像；采样点 <5 也要声明 |
| 活动会话历史（ASP）可用 | Active Session History | 数据库侧时段不可判定 |
| logrpt 可用 | 配对 analyze_log HTML | 日志轴写"数据不足"，不得编造 |
| se 可用 | `vb_tool se` | 事件只按 AWR 数字判，标"se 未收录" |
| 源码根可用 | workspace/src | 事件分析止步于 se 语义层 |

另注意空载窗口：AAS 极小、DB Time/Elapsed < 1% 时，所有"占比"结论先质疑分母
（小分母会把无害事件放大成"高占比"，实例见 `metrics.md` 计数型事件节）。

### 第 1 步：整体负载画像

为什么必须先有整体画像再下钻：没有全局定位就逐章翻，会把局部正常当异常。
取数：报告头（逻辑核数 N、Elapsed、DB Time、AAS）、Time Model（CPU_TIME/DB_TIME）、
OS Statistics（busy/iowait 窗口均值）。

1. AAS = DB Time / Elapsed；每核 = AAS/N（>1 超核 / 0.5~1 接近 / <0.5 余量）
2. 数据库资源占用 = DB Time / (Elapsed × N)
3. CPU-等待方向 = CPU_TIME / DB_TIME（≥70% 偏计算 / <40% 偏等待）——只定方向

**口径校核（判读 VastBase 时间数字的前提，详见 `metrics.md`）**：
CPU_TIME 含后台线程、事件不分前台后台、%DBtime 可 >100%——这些数字是方向不是账本。
"偏计算"的结论必须用 OS 分钟序列佐证（busy 高 + 运行队列 r>N）；OS 安静而库内
CPU_TIME 高，说明是后台线程耗 CPU，去查 Callstack 后台堆栈。"偏等待"的结论必须用
ASP 桶等待计数或 Top Event 真实等待佐证。

产出一句整体判定（进报告总体结论段）：本窗 AAS、每核比、资源占用、CPU-等待方向
（注明口径）、OS busy/iowait，以及优先下钻方向。

### 第 2 步：时间轴定位异常时段

为什么看时间轴：窗口均值会稀释几分钟的尖刺，而绝大多数性能事故是时段性的。

四个数据轴（digest 已自动计算与标注）：

1. **OS 分钟序列**：CPU（busy>80%、iowait>10%、r>N、b>N 的 5%；或 r/b ≥ 2×中位的相对异常）、
   内存（MemAvailable<10%、pswpout>0.5/s、pgmajfault>50/s）、磁盘（**先看 Rot 列定介质**：
   SSD await>5ms 异常、HDD await>20ms 异常；util 永不作判读标准，2026-10-28 用户令）、
   网络（drop>100/min、Retrans%>3~5%、RTT>20ms、ListenDrops>0）。
   异常分钟合并（间隔 ≤3min）；≥2min 为持续型，单分钟为尖刺。
   **命中任一异常后必须走 `metrics.md`「OS 指标关联判读」成组核（同向/分流/分层/时间对齐）——
   单指标只产生怀疑，不许单指标下结论**
2. **ASP 5 分钟桶**：max_active_sess ≥ max(1.3×中位, 1.5×AAS, 10)；各等待类逐秒计数
   峰值超 detect 层阈（锁 3/轻锁 3/IO 3/WAL 2/事务 5=时轴发现层；机械闸警戒=2×、异常=4×，三层口径见表 D）；waitchain 直接给出
   根阻塞会话与受害 SQL
3. **日志切片**：每个异常时段切两窗——P=[t0−10min, t0) 触发区与 W=[t0, t1] 症状区，
   对比错误首末落点与慢 SQL 前后堆积，判断谁先谁后（详见 `log-analysis.md`）
4. **多源对齐**（五源：OS 指标 × 活动会话采样 × 日志 × 后台堆栈 × 刷脏/长事务序列）：
   digest 已拼好对齐表。时段结论要求至少两源同向，单源尖刺降为观察项

OS 全程安静不是"无问题"的结论，转第 3 步看数据库侧。

**OS↔DB 跨层对齐（先落库侧影，再下机制）**：每个 OS 异常在成组核成立后，先按
`metrics.md`「OS ↔ DB 关联」方向 A 落到 DB 侧——这个 OS 异常影响库里的哪些等待
事件、哪些 SQL、多少 DB Time（对不上账 = 库外因素，见方向 A 表）；DB 侧异常则按
方向 B 去 OS 侧查证根因。两向对完再下机制层。

**OS 根因下机制层（强制，对称于第 4 步 DB 侧形态锚）**：落完库侧影后，必须沿
`metrics.md` OS 表「机制」列 → `../linux/` 对应文件
（cpu / memory / io-storage / network / file-descriptors），读该指标的
机制节 + 判读速查表 + 常见错误节，把「机制层为什么」（内核/块层/协议栈的哪条
路径放大它、什么参数/配置动它）写进发现的根因——**根因必须到机制层，不许停在
数字层**。OS 指标的口径陷阱与内核机制本体不在此文件展开，展开在 linux 文件里。



### 第 3 步：等待事件溯源

**必要条件闸门（2026-10-27 用户令）：事件 %DBtime ≥ 10%**——不到 10% 的等待
事件一律不进本步、不定位为异常（不进问题卡；确实值得留意的最多写数据局限/
观察项）。占比 10% 是"值不值得花溯源成本"的硬门槛，不是"过线即异常"——过闸后
仍须走完取证链才能定论。

过闸事件按特征定溯源侧重：平均等待超阈（IO ≥20ms / 锁类 avg ≥100ms 警戒·
≥1000ms 异常——RULES 单源，旧"重量锁 100/轻锁 10"口径作废 2026-11-05）走重取证；
高频但平均 ≈0 的先按 `wait-events.md` 计数型识别法
甄别（计数型事件是访问量镜像，甄别为计数型的不再当等待溯源）。

对每个过闸事件走 `wait-events.md` 的溯源链：事件分类定性 → `vb_tool se` 取语义与
源码触发点 → 堆栈指纹 → 源码函数核对（回答：前台还是后台路径、竞争什么资源、
哪些参数/计划形态/并发度放大它）。只有数字没有机制的，最多写观察项。

机制确认后立即翻 `parameters.md` 对应分组取当前值进证据。

### 第 4 步：瓶颈形态过闸与 SQL 定位

**强制过闸**（2026-10-26 立，全域纪律见 `bottleneck-patterns.md` 强制过闸节）：
第 1~3 步与健康总览表亮出的**每个 ■/▲ 异常项，必须在 `bottleneck-patterns.md`
P1~P12 形态表逐项登记命中/排除**，排除带数字依据，登记表进工作底稿。命中形态
走该文件取证链取证定论，再按 SQL 九维定位主要责任 SQL（维度选择、频次型与
单次贵的区分、跨维矩阵定责）。定论后挂**形态→机制锚索引**的机制文件做
"为什么"层解释（根因必须到机制层，不许停在数字层）。
全排除的异常项显式写"根因未定 + 缺什么数据"。

### 第 5 步：根因结论与参数对照

只对判入的形态做。每个发现四要素：

1. 根因一句话（内核机制用 DBA 语言写，源码级深度保留）
2. 证据：至少两个章节的数据互证并带数值（单章节证据降为观察项）
3. 影响面：占 DB Time 多少（注明佐证口径）、波及哪些 SQL/对象/会话
4. 建议：改 SQL/计划在前、调参在后；参数类建议按 `parameters.md` 落成
   参数名 = 当前值 → 建议值 + 理由

参数对照四查（详见 `parameters.md`）：机制查（源码机制指向的参数）、配比查
（内存池之和 vs max_process_memory）、介质查（Rot 与 random_page_cost/预取匹配）、
OS 查（sysctl Begin≠End = 窗内改过，单列证据）。

## 报告要求

- ★**只报问题（2026-10-26 用户令）**：报告的每一段都必须是问题或问题相关。
  - 健康总览表只列 ■异常/▲警告；正常项/参考项不进表，用一句
    "其余 N 项正常/参考（不展开）"带过（`overview_table.py` 已按此过滤）
  - 不写"某某方面正常""某某无异常""本窗未发现复制问题"这类背书句；
    常规指标、画像数字只服务于问题判定，不单独成段
  - 够不上问题的信号不写（2026-11-02 用户令：数据局限/留意项整个章节砍掉，
    无意义；真正的数据缺口在附录 C 一句带过）
  - ★**非问题不立卡（2026-11-04 用户令，"核查为伪象"也不许占卡）**：
    定性为非问题（分母失真/统计口径伪象/无饱和佐证的瞬时尖峰）的项不写问题卡、
    不占编号。抑制在闸层完成（`overview_table.py` 守卫：r 尖峰 busy 佐证、
    Plan Time/读占比/命中率分母地板、死元组率分母守卫，全量清单见
    `check-inventory.md` 表D 与版本注记）；守卫未覆盖而分析定性非问题时，
    正文同样不立卡，附录 C 一句登记
  - 长度上限：现象 ≤2 句、证据表 ≤4 行、原因 ≤3 句、建议 ≤3 条；
    总体结论正文 ≤3 句。写不下就是没想清楚，先删再写
- 按 `report-template.html` 输出到输入同目录，文件名 `<输入名>_analyze.html`。
  模板头部注释即生成规则，逐条遵守
- ★版式四令（2026-11-02 用户令）：深色专业主题（模板已固化，系列色=dataviz
  校验过的暗面 8 槽，改色先跑 validate_palette.js）；图表放附录 A 开头、正文只留
  结论与问题卡；不设"数据局限与留意项"章节；面板双列卡片
- **图表义务**：把 charts.json 全文粘进模板 `const DATA`（渲染器自动画分钟级面板、
  5 分钟桶面板，含悬停取值；★不画问题时段底纹带图，2026-11-03 用户令）。
  不手写 SVG、不手改数据。确实没有
  数据（旧格式报告）才允许面板置空，并在附录 C 声明
- 每个发现写清四件事：是什么、不是什么、影响多大（占 DB Time 比例 + 佐证口径）、
  优先级多高。定不了论的在问题卡内标"根因未定 + 缺什么数据"，不和稀泥
- **根因闭环对账（2026-10-26 立）**：报告含健康总览表时，交付前逐行核对——
  表里每个 ■/▲ 项必须在正文问题卡有对应根因段（机制层"为什么"），
  或显式标"根因未定 + 缺什么数据"；对不上账的项补分析，不许表里亮了正文不接。
  每个根因标注对应形态编号（P1~P12）
- ★**交付前三查（2026-10-27 立，参照 DBAIOps arXiv 2508.01136 的人评三标准
  Root Cause Recall / Theoretical Consistency / Evidence Authenticity）**：
  渲染验证之外，交付前跑 `python3 scripts/selfcheck.py <报告>.html <digest> <charts>`
  并逐条处置输出：
  ①**根因召回**：总览每个 ■/▲ 行的指标名或数值必须在正文复现（脚本报 [闭环]）
  ②**机制一致**：每条根因挂形态→机制锚，因果链成串——模型自查，脚本不覆盖
  ③**证据保真**：正文数值 token 全部回查 digest/charts（脚本报 [证据]）；
  UNTRACEABLE 逐条处置——衍生计算值在正文留算式、环境元信息注明出处、
  确无出处即改引 digest 原值或删除。判例：DBAIOps 论文里基线方法引用了
  不存在的指标值直接判 0 分——数值无出处不是风格问题是硬伤
- IO 延迟结论必须先报盘体（Disk I/O per device 的 Rot 列，0=SSD 1=HDD），再按介质
  阈值判读；混盘分别说
- 参数类建议必须写 参数名=当前值→建议值+理由；报告未含的参数写进数据局限并注明
  需实机确认，不猜默认值
- 建议列表只放可执行动作："不做某事"的论证（如参数为何不上调）属于原因分析，
  不进建议；条件性动作写明触发条件与需盯的监控项
- 涉占比的结论写明用哪条独立口径佐证（AAS / ASP 桶计数 / OS 序列）
- 证据一律表格：数据 | 数值 | 出处（源报告章节名）| 说明
- 严重度用图标+文字双编码（● 严重 / ▲ 需要处理 / ◆ 留意），不单靠颜色
- 继承规范：日志 P 前十分钟窗与 W 症状窗分开表述；错误组声明首尾覆盖与计数口径；
  STATUS 类事件不计入等待；Elapsed <60s 声明窗短；比例结论随窗口质量降档
- 分析方法论词汇（阶段名、五源、口径校核等）只进附录，正文用 DBA 正常语言

## 常见错误

| 错误 | 为什么错 | 纠正 |
|---|---|---|
| 数值直接从 HTML 抄 | 手抄易错且无对账 | 一切数值引用出自 digest |
| 跳过预检直接看 Top SQL | 重启/回卷窗口的差值全是噪声 | 第 0 步不过先降级并声明 |
| 单章节证据直接定论 | 单源可能有采样偏差或记账失真 | 至少两章节互证，否则降观察项 |
| IO 结论不报介质 | SSD/HDD 阈值差 4 倍，混判必错 | 先看 Rot 列再选阈值 |
| 把 STATUS 事件算进等待占比 | STATUS 是执行阶段标记不是等待 | 只用真实等待类事件 |
| 高频零延迟事件当锁瓶颈 | 计数型事件是访问量镜像不是阻塞 | 按 `wait-events.md` 计数型识别法核源码 |
| 占比结论不注明佐证口径 | VastBase 口径下 %DBtime 可 >100%，各类不可加 | 每个占比给独立佐证口径 |
| 参数建议只写"建议调大" | 无法执行也无法复核 | 落成 参数名=当前值→建议值+理由 |
| 报告正文写阶段编号等内部术语 | 读者是 DBA/业务方，不是流程作者 | 方法论只进附录 |
| 把正常项/画像数字写进正文 | 47 项里绝大多数正常，逐条点名=报告被噪声淹没，问题反而找不到（2026-10-26 用户令"都是有问题的，说关键点"） | 只写问题项；正常项一句带过 |
| **闸亮 ■/▲ 就立卡（哪怕定性为伪象/非饱和）** | "核查为空载小分母放大/统计伪象/瞬时尖峰"这类卡对读者是没价值内容（2026-11-04 用户三连点名问题 3/4/5） | 非问题项在闸层守卫抑制；守卫漏网的分析定性非问题后正文不立卡，附录 C 一句登记 |
| **数值四舍五入改写 digest 原值**（509.753→509.8、1.68→1.7） | 改写值在 digest 里定位不到=证据失真；旧 selfcheck"整数子串命中"让改写值全漏过 | 原值照抄，展示截断只丢小数尾；selfcheck 已收紧为前缀对账（2026-11-04） |

| **修复只改当份报告不固化 skill** | 同类错误下一份报告必复发（2026-11-04 用户令："要改 skill 逻辑"） | 每处修复必须落规则：模板生成规则 / 本文件 / selfcheck / overview_table 至少其一 |
