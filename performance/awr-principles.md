# AWR 找线索的原理层（数字为什么能当证据）

## 概述

AWR 诊断的本质：把"数据库的时间花在哪"记成**三本账**，诊断=三本账互相对账。
本文件回答"为什么这条数字能/不能当证据"——记账原理与原理性盲区。流程层看
`awr-report-analysis.md`（六步）；单指标口径看 `metrics.md`；章节字典看
`awr-report-reference.md`。四份各管一层，本文件是最底下那层。

判读前先问一句：**这个数出自哪本账、怎么记的、盲区在哪**——三问答不上来的
数字不进证据表。

## 概念：三本账

| 账 | 成员 | 记账方式 | 原理性推论 |
|---|---|---|---|
| **账一：计数器差分** | pg_stat_* 系、Time Model、九维 SQL 榜、Load Profile | 区间末−区间初，精确但**无时刻** | 差分窗口内重启/回卷=作废（第 0 步预检的根据）；**gauge 与 counter 必须分清**——dead tuples/表年龄是存量值，负增长 WARNING 出现即记账前提被破坏；unique_sql 全量计数 ⇒ **采集 SQL 自身进榜**（采集指纹） |
| **账二：采样** | ASP（5 分钟桶）、OS 分钟序列、Callstack 堆栈 | 周期抓瞬时，**有时刻但不穷尽** | 单线程采样器几千会话下扫不完一圈 ⇒ **avg 被系统性压低**（实测 avg 180 / max 2065 / AAS 1623——对账用 max_active_sess 对 AAS 的量级，不比 avg_sess）；5 分钟桶糊掉桶内尖刺；堆栈只是采样点不是全量 |
| **账三：OS 内核账** | /proc 差分（stat/vmstat/diskstats）、ss 瞬态 | 与库内记账**完全不同源** | 库内外对账的根据：同向=实锤因果，对不上=库外因素或口径问题（`metrics.md` OS↔DB 关联两向表） |

三本账时间粒度不同（差分区间 / 5min 桶 / 1min 序列）——**多源对齐就是在三本
账的时间轴上找同向证据**，这也是"每个异常时段至少两源同向"规则的原因。

## DB Time 的记账边界（源码定论）

计时区间 = `PostgresMain` 里 `ReadCommand()` 返回之后 → `timeInfoRecordEnd()`
（postgres.cpp:8975/:8809/:8868）。由此推出四条边界：

1. **不计入 DB Time**：会话初始化（线程派生/认证/InitPostgres）、命令间空闲、
   会话退出清理、**RECV-Q 里排队的连接**——排队堆积不代表 DB Time 涨
2. **计入但无事件标签**：命令内向客户端 socket 写结果的阻塞计入 DB Time，
   但等待事件账本没有对应条目（NET_SEND_TIME 需 enable_record_nettime +
   驱动支持）——这就是"**高 AAS + 低 CPU + 低事件占比**"标准组合的出处：
   库在等客户端消费结果集，账本上却查不到去向
3. **口径三陷阱**（数字是方向不是账本）：CPU_TIME 含后台线程；事件不分前台
   后台；%DBtime 可 >100%、各类不可加
4. **空载分母**：DB Time/Elapsed < 1% 时所有占比结论先质疑分母——小分母把
   无害事件放大成"高占比"

## 等待事件账本的原理与三类污染

事件是时间去向的记账单位；**定量三件（%DBtime / Total Wait / Avg）是"影响
多大"的唯一来源**，丢不得。但账本有三类系统性污染，定性时先甄别：

1. **STATUS 类**（76 个）= 执行阶段标记，不是等待——一律不计入等待占比
2. **计数型** = 访问量镜像：调用一次记一次等待但 avg≈0（实测 BufHashTableSearch
   71 亿次 avg=0）——高频 + avg≈0 先按计数型识别法甄别（`wait-events.md`），
   甄别为计数型的不再当等待溯源
3. **高频 avg≈0 的第三种可能** = 测量括号：临界区极短，计时精度包住的是
   测量开销本身

**自旋盲区**（账本结构性缺口）：重量级锁的跟随者自旋等待**不进任何等待事件
账本，只表现为 CPU**（`../internals/locks.md` 自旋节）——"CPU 高 + 事件全低"
的三分支之一（另两支：后台线程耗 CPU / 客户端消费不动）。

**waitchain 的适用边界**：机制根源是 gs_asp.block_sessionid **仅重量级锁填充**
——LWLock 在 ASP 里没有阻塞关系，持有者要走 `pg_stat_get_backend_lwlocks()`
专有视图或前台堆栈（`wait-events.md` 源码定论节）。

## 四问各对应哪本账

| 问 | 账 | 失败模式（丢了会怎样） |
|---|---|---|
| ①定量：影响多大（event %DBtime ≥10% 才溯源） | 账一 | 不定量就把小事当根因，或大事漏报 |
| ②现场：谁在等谁（ASP 桶/waitchain） | 账二 | 只有总量没有现场，定不了"谁锁谁" |
| ③责任：谁的 SQL（topsql 占比大优先查） | 账一 | 找到机制找不到责任方，建议落不了地 |
| ④机制：为什么（堆栈/源码/OS） | 账三+源码 | 数字对齐但解释停留在表象，复发 |

四问答不齐要么继续取证要么显式"根因未定 + 缺什么数据"，禁止只报数字。

## 常见错误

| 错误 | 为什么错 | 纠正 |
|---|---|---|
| 把 gauge 当 counter 差分 | 存量值相减无意义（dead tuples 是快照存量） | 先分清存量和增量再取数 |
| 拿 avg_sess 对 AAS | 采样器扫不完一圈，avg 系统性偏低 | 比 max_active_sess 与 AAS 的量级 |
| 单本账定论 | 每本账都有原理性盲区（见上表） | 至少两源同向才进结论 |
| 采样缺失当零 | "桶里没采到"≠"没有发生" | 缺数据写数据局限，不写正常 |
| 排队连接多推断 DB Time 虚高 | RECV-Q 不计 DB Time（边界 1） | 先对 max_active_sess 量级再下结论 |

## 版本注记

- DB Time 计时边界为 openGauss 6.0.0 源码定论（G100 V3 档基线）；NET_SEND_TIME
  依赖编译/驱动开关，现场以实测定
- ASP 5 分钟桶、OS 分钟序列为 vb_tool 2026-10 档采样构成；旧版报告无分钟序列
  时账二降级（六步第 0 步处理）
