# cases/ — 案例库（MOS 式判例层）

机制文件回答"为什么会这样"（法条），案例回答"上次遇到是这样解的"（判例）。
每个案例都是一次真实诊断的固化：症状→排查链→根因→处置→预防，并**回链**
到支撑它的机制文件——机制结论靠案例验证升级，案例靠机制获得解释力。

## 文件与命名

- 命名：`case-<环境代号>-<症状slug>-<yyyymm>.md`（小写连字符；环境代号
  内部用真实代号，**发布 GitHub 前整体替换为 env-N** 并核一遍）
- 每案例固定骨架：

```
## 环境（版本档/部署形态/资源）        # 中性化，不写客户名与真实 IP
## 症状（业务视角+监控读数）
## 排查链（按时间序：命令→读数→判断）  # 保留走错的路——判读经验在弯路里
## 根因（挂机制文件 file:line）
## 处置与结果
## 预防（参数/巡检/监控项）
## 关联知识文件                          # 双向：机制文件也要补"案例锚点"
## 遗留（未验证项/后续）
```

## 铁律

1. **只收真实案例**——不虚构、不拼凑；细节不可考就标⚓或"待补"
2. **脱敏**：客户名/真实 IP/主机名一律代号；引用的报告先入
   `workspace/inbox/` 原件，案例内只放摘录
3. 排查链必须**可复演**（命令原文），结论必须**可追溯**（file:line 或文档）
4. 案例结论与机制文件冲突时：以源码复验为准，冲突本身就是知识条目

## 入库流程与来源

原料（报告/日志/会话记录）→ `workspace/inbox/` → 复盘成文 → 本目录 +
`INDEX.md` 登记 → `python3 scripts/check_graph.py` 全绿。来源四路：

1. 现场报告样本（成对 awr+logrpt）
2. 历史战役复盘（测试环境实战）
3. **VastBase 官方文档已知问题（docs.vastdata.com.cn，主源）**
4. 开源 openGauss issue tracker（**近似参考**——基线近似原则同 ha/；
   拉取配方见 ROADMAP 挂账）
